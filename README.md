# NoHandWrite

少量の手書き入力からその人の字体を学習し、文字を生成します。

1. **補正** — 書いた文字を字体を保ったまま綺麗にする(中村ら「[平均文字は美しい](https://dl.nkmr-lab.org/papers/196/paper.pdf)」EC2014 のフーリエ級数平均を実装)
2. **生成** — 書いていない文字をその字体で生成する([SDT](https://github.com/dailenson/SDT), CVPR 2023 の日本語学習済みモデルを利用)
3. **出力** — ペンプロッター用の単線SVG / G-code を書き出す。GRBL機ならUSB経由で直接送信もできる(実験的)

全パイプラインがストローク(筆順付き点列)ベースで、Windows / Mac 両対応(ブラウザUI)。

## セットアップ

必要なもの: [uv](https://docs.astral.sh/uv/), Python 3.11+

```sh
uv sync
```

### SDT(未入力文字のAI生成)を使う場合

`third_party/SDT` に学習済みモデルとデータ辞書が必要です(なくても補正・入力は動作します):

- 学習済みモデル → `third_party/SDT/model_zoo/saved_weights/Japanese/checkpoint-iter147999.pth`
- 日本語データセット(のうち `Japanese_content.pkl` などの辞書) → `third_party/SDT/data/TUATHANDS_JAPANESE/`

入手先は [SDTのREADME](https://github.com/dailenson/SDT#-pre-trained-model)(Google Drive)。データセットはTUAT HANDSに由来する研究用データです。**研究・個人利用の範囲で使用してください。**

## 起動

```sh
uv run uvicorn server.main:app --host 0.0.0.0 --port 8765
```

ブラウザで http://localhost:8765 を開く。

- **✏️ 入力** — お題文字を手書きで入力(推奨: 「スタイル学習+英数字(87字)」)。「回数」で同じ文字を複数回書いて平均文字の精度を上げられる(順序は「セット全体をN周(推奨)」か「連続N回」)。「入力枠」スライダーで書く領域の大きさを変更可能
- **📚 ライブラリ** — 書いた文字の重ね描きと平均文字(赤太線)を確認
- **🖋 生成** — テキストを入力すると、書いた文字は平均文字、未入力文字はAI生成で描画。SVG / G-code をダウンロード
- **🖨 組版** — 文章をmm指定(文字サイズ・文字間・行間・行幅・余白、A4/B5の用紙プリセットあり。文字間は負の値で詰め組みも可。字送りはデフォルトで可変幅=各文字の字幅で送り、チェックを外すと従来の等幅。縦書きモードあり=右から左への段組みで、ー・括弧類は90°回転、句読点・小書き仮名は右上寄せ)でページにレイアウトし、プレビューを確認してペンプロッター用G-code(送り速度・ペン上下コマンド・Y軸反転も指定可)/ SVG を出力。行の折り返しには簡易禁則処理つき(行頭に来られない「。」「ー」「っ」などは追い出し、句読点はぶら下げ、開き括弧は行末に残さない)。筆圧はプレビュー・SVGの線幅と G-code のZ変調に反映できる(下記)

### iPad + Apple Pencil で入力する

同じWi-Fi上のiPadのSafariから `http://<Macのローカル(LAN)IP>:8765` を開くだけです(サーバは `--host 0.0.0.0` で起動)。Apple Pencilの筆圧も記録されます。MacのIPは システム設定 → Wi-Fi で確認できます。

## データ

`data/<書き手ID>/uXXXX.json` に1文字1ファイルで保存(座標・時刻・筆圧、複数回分)。git管理外です。

描画結果のキャッシュは `data/.render-cache/<書き手ID>/` に置かれます(消しても再生成
されるだけで、消して困るものではありません)。

## 生成のキャッシュ

組版ページで文章を1文字直すたびに全文字を作り直すのは無駄なので、1文字ぶんの描画結果
(平均文字/AI生成)は `core/nohandwrite/rendercache.py` にキャッシュされます。メモリと
ディスクの2段構えなので、サーバーを再起動しても既に描いた文字はモデルを読み込まずに
返ります。

キャッシュキーには**その描画が依存したものすべて**が入ります — 書き手・文字・平滑化の
有無に加えて、元になったサンプルファイルの指紋(`Store.char_stamp`)です。平均文字はその
文字自身のサンプル、AI生成はSDTに渡すスタイル参照15字のサンプルが指紋の対象なので、
書き足し・取り消し・削除をすれば該当する文字だけが自然に作り直されます。

ゆらぎ(`variation.jitter_strokes`)はキャッシュの外側で毎回かけるので、同じ字が複数回
出てきても、また同じ文章を組み直しても、一文字ずつ違う形のままです。

明示的に引き直したいときは、生成ページの「↻ 再生成」(その字だけ)、両ページの
「↻ 全部作り直す」、または `POST /api/cache/clear` を使います。SDTのデコードは決定的で、
毎回変わるのはスタイル参照の引き直しだけなので、再生成は本当に新しい試行になります。

## 入力内容の保持

ページを移動しても、打った文章と選んだ書き手はブラウザに残ります(localStorage、
`web/remember.js`)。生成ページで「✏️ 自分で書く」→入力ページ→戻る、という往復でも
文章は消えません。

- `nhw-text-generate` / `nhw-text-typeset` — **ページごとに別**です。組版ページには手紙
  一通が入っていることが多く、1字調べに生成ページへ寄っただけでそれが消えては困るため
- `nhw-writer` — 入力ページが以前から使っているキーをそのまま読み書きします。3ページで
  同じ「誰の字か」を見るので、文章だけ復元して書き手が別人に戻る、という事故が起きません

保存は入力の300ms後、加えて `pagehide` でも書くので、打ってすぐリンクを踏んでも最後の
数文字が落ちません。Safariのプライベートモードは localStorage が例外を投げるため、
読み書きはすべて握りつぶしています(保持されないだけでページは動きます)。

## 進捗の表示

未入力の文字が多い文章は、プレビュー1回が数十秒かかります(初回はSDTのチェックポイント
読み込みだけで数秒〜十数秒)。その間ずっと「レイアウト中…」のままだとフリーズと区別が
つかないので、リクエストは**クライアントが作ったジョブID**を持たせ、ブラウザは
`GET /api/render/progress/<job>` を0.4秒おきに見に行きます。

```
レイアウト中…
SDTモデルを読み込み中(初回のみ・数十秒かかります)… 4秒
未入力の文字をAI生成中 8/26 字… 8秒
生成をやり直し中(うまくいかなかった字) 4/4 字… 13秒
プレビュー更新
```

段階は `starting / samples / style / model / generate / retry / layout / export / done`。
生成の進みは `SDTGenerator.generate(on_progress=…)` がバッチごとに報告します(1バッチ8字
なので、カウンタは8字きざみで動きます — その間も経過秒数は毎秒進みます)。

進捗は `server/progress.py` の小さな板に載るだけで、直近32件を超えると古いものから消え
ます。途中でブラウザを閉じても後片付けは要りません。ジョブIDを付けずに叩けば(APIを直接
使う場合など)何も記録されません。

## 生成できなかった文字の扱い

書けない文字は出力では**空白**になります。何も言わずに紙まで届いてしまわないよう、
下記で知らせます。

- 生成ページ: 字ごとのタイル(赤枠=不可、橙枠=要確認)と、上部の一覧
- 組版ページ: プレビュー上部の一覧(→ 生成ページへのリンク付き)とページ情報の字種内訳
- SVG/G-codeのダウンロード: レスポンスヘッダ `X-Missing-Chars`(パーセントエンコード)を
  見て「○○は空白になっています」と表示
- プロッターへの直接送信: `POST /api/plot` のレスポンスの `missing`

理由は `mode` と `reason_code` で区別されます — `unsupported`(SDTの辞書にない)、
`decode_failed`(生成したがストロークが得られなかった)、`model_missing`(SDT未設置)、
`truncated` / `few_strokes` / `low_score`(生成はできたが要確認)。

## 全角/半角の代用

（）と()、；：と;: は同じ記号の幅違いですが、手書きサンプルもSDTの辞書も普通はどちらか
片方しか持っていません。「全角/半角を代用」(既定ON)をオンにすると、**対応が良いほうの
字形**で書きます — 自分で書いた（ > SDTが生成できる( > どちらでもない、の順です。

対応表は `core/nohandwrite/widths.py`(ASCII ↔ 全角形 U+FF01–FF5E、および半角CJK約物
｡｢｣､･ｰ)。禁則処理・縦書きの字形回転(`export/layout.py`)とグリフメトリクス
(`metrics.py`)も両方の幅を見るので、代用しても行頭行末の扱いや字の大きさは変わりません。
オフにすると打った文字をそのまま扱います。

## 設計メモ: 文字サイズの正規化

かつては「自分の筆跡 = 入力欄に書いた大きさのまま(field-relative)」「AI生成 = 字面をボックス一杯に拡大」と正規化方法が分かれており、組版で混在させると生成文字だけ2〜3倍大きく見える問題があった。検討した解決法は2つ:

- **案A: 生成文字を書き手に合わせて縮小** — スタイル参照に使った平均文字の字面占有率(中央値)を測り、SDT出力をその大きさに縮める。書き手のサイズ癖(句読点を大きく書く等)が残る利点があるが、入力欄のどこまで使って書いたかに依存するため、セッションや端末で出力サイズがばらつく不安定さは残る。
- **案B(採用): 全文字をbbox正規化 → 共通メトリクス表で配置** — 筆跡・生成とも `normalize_strokes` で字面をボックスに合わせたあと、`core/nohandwrite/metrics.py` のルール表(文字種デフォルト: 漢字0.90 > かな0.82 > 英数字0.72 など+個別文字の縮小率・アンカー: 小書き仮名、句読点、括弧、英小文字のx-height/ディセンダー等)で縮小・配置する。サイズの一貫性が構造的に保証され、入力の書き方にも依存しない。代わりに書き手固有のサイズ癖はルール値に置き換わる。

サンプルは元座標のまま無劣化保存されており正規化は処理時に行うため、既存データの移行は不要(方式はいつでも戻せる)。ライブラリ画面の平均文字(赤太線)だけは生サンプルと重ねて表示する必要があるため、従来どおり field-relative(`beautify(place=False)`)で描画している。

## G-code について

出力はmm単位・絶対座標、ストロークはRDPで簡略化済み(許容誤差0.05mm)。組版ページの
「ペン方式」で機械に合わせます。

- **サーボ(デフォルト)** — ペン上下は `M3 S40` / `M3 S90`。S値は機械に合わせて調整。
  GRBL 1.1 なら `$32` を 0(レーザーモードOFF)に。1にするとG1移動中しかスピンドル
  出力が出ず、ペンが正しく上下しません。GRBL 0.9 系に `$32` はなく、代わりに
  `VARIABLE_SPINDLE` を有効にしてビルドしたファームでないと `M3 S…` が効きません
- **Z軸** — `G0 Z5.0` / `G1 Z0.0 F300`

サーボは指令を受けてから動き終わるまで時間がかかるのに、GRBLは次の行をすぐ実行して
しまいます。そのため**ペン上下のたびに `G4`(ペン待ち)を挟みます**(デフォルト0.25秒)。
これがないと線の描き始めが欠けたり、上げきる前に動いて紙を引きずったりします。Z軸機は
0にして構いません。描画送りのデフォルトは 750 mm/min(ペン描画向けの控えめな値)。

**用紙原点** — 「用紙の左下を機械原点にする」をONにすると、用紙サイズを基準にY反転する
ので、**機械の原点を紙の左下に合わせておけば文章量に関係なく同じ位置に描かれます**。
OFF(または用紙=自由)のときの原点は本文ブロックの左下なので、行数が変わると紙の上の
位置がずれます。

終端は `G0 X0 Y0` → `M5` → `M2`。

## プロッターに直接送信(実験的)

組版ページの「プロッターに直接送信」から、GRBL機にUSB経由でそのまま送れます
(`server/plotter.py`)。macOSでは `/dev/cu.*` のポートだけが候補に出ます。

- GRBLの文字数カウント方式でストリーミングします(受信バッファ128バイトを埋めたまま
  送り続ける)。1行ずつ `ok` を待つ方式だと、手書きの細かい線分ごとに動きが途切れます
- 送信前にペンを紙の左下(原点)に合わせてください。「送信開始位置を原点にする」
  (デフォルトON)で `G92 X0 Y0` を送り、**その位置を機械に原点として教えます**。
  出力は絶対座標なので、これがないとGRBLが以前から持っている座標系のまま描き、
  最初にその差分だけ移動してから描き始めます(描画そのものは正常に見えるため
  気づきにくい)。オフにすると機械側の原点をそのまま使います
- 送信開始時にGRBLへ `?` を投げ、そのときの機械位置をUIとサーバログに出します。
  位置がずれるときはここを最初に見てください
- GRBLがアラーム状態(ホーミング有効時の起動直後など)なら送信を中止します。
  「$Xでアンロック」にチェックを入れると `$X` を送ってから開始します
- 「停止」は フィードホールド(`!`)→ ソフトリセット(`\x18`)→ `$X` → ペン上げ の順に
  送ります。**リセットで機械の位置が失われるので、原点を取り直してください**

実機がなくても、擬似シリアル(pty)に偽GRBLを立てた `tests/test_plotter.py` で
プロトコル・アラーム時の中止・停止シーケンスを検証しています。

## 機械が指令どおりに動かないとき

出力するG-codeはmm単位の絶対座標そのものなので、ファイルが指示していない場所へ
機械が動く場合、原因はコントローラ側(キネマティクス・steps/mm・ワーク座標の
オフセット)です。`scripts/grbl_probe.py` で機械に問い合わせられます。

```sh
uv run python scripts/grbl_probe.py            # 設定を読むだけ(動きません)
uv run python scripts/grbl_probe.py --jog X 50 # X方向に50mm動かす
```

**ベルト1本でXYを動かす機械(CoreXY / H-bot)は要注意。** CoreXY はモーター2個を
同時に回して斜めに動かす方式で、ファームウェア側も CoreXY ビルドでないと噛み合い
ません。Cartesian ビルドのまま CoreXY 機に載せると、指令 (x, y) が実際には
**((x+y)/2, (x−y)/2)** の動きになります。たとえば `G0 X10 Y285` は
「右に147mm・手前に137mm」という別物の動きになります。`--jog X 50` で真横に50mm
動けば正常、斜め45°に約35mm動くなら不一致です(GRBLでは `config.h` の
`#define COREXY` を有効にしてビルドし直す必要があります)。

**用紙原点をONにするときは可動範囲を確認。** A4縦なら最初の移動でY方向に285mm
必要です。機械の可動範囲がそれより狭いと、端に突き当たって脱調します
(ソフトリミットを切っているGRBLは止まらず、そのまま鳴り続けます)。
`grbl_probe.py` の `$130` / `$131` で可動範囲を確認できます。

送信パネルの「可動範囲X / Y」に機械の値を入れておくと、**そのジョブが実際に必要と
する最大X・Yを送信前に計算し、超えていればポートを開く前に中止します**(0で無効)。
可動範囲より大きい紙に書きたい場合は「用紙の左下を機械原点にする」をオフにして
ください。原点が本文ブロックの左下になるので、必要なストロークだけで済みます。

## 筆圧の反映

Apple Pencil などで記録した筆圧は平均文字にも通っており(フーリエ平均の第3成分)、出力に反映できます:

- **SVG** — 組版ページの「筆圧で線幅を変える」で、筆圧に応じた可変線幅(0.2〜1.0mm)で書き出す。プレビューにも同じ線幅が出る。プロッターに送る単線SVGが欲しいときはオフのまま
- **G-code** — 「筆圧をZ軸に反映」で、描画中のZ座標を筆圧弱〜強の2値の間で変調する(柔らかいペンなら筆圧が線幅になる)。**Z変調に対応していないプロッター(サーボ式ペンリフトなど)はこのチェックを外す**と従来どおり固定のペン下げコマンドになる

筆圧データがない文字(マウス入力・AI生成)は自動的に固定幅・固定Zで描かれます。
