# 生成品質・カバレッジ改善プラン

SDT生成には現在2つの問題がある。(a) 画数の多い漢字(鬱・鑑・驚など)が崩壊しやすい、(b) 学習データに含まれない字(鹵などの常用漢字外)がそもそも生成できない。本ドキュメントはコード調査で特定した原因と、再学習なしの短期対策からファインチューニングによる根治までの対策をまとめる。

## 現状と原因

### (a) 多画数漢字が崩壊する仕組み

崩壊は単一の原因ではなく、3つの要因が重なって起きている。

- **推論の打ち切り** — `core/nohandwrite/generate/sdt_adapter.py` の `MAX_SEQ_LEN = 120`。SDTの `inference()`(`third_party/SDT/models/model.py`)は全文字が終端フラグ s3=1 を出すまで自己回帰するが、120点で強制終了する。鬱のような長軌跡の字は途中で切れるが、「切れた」ことを示すシグナルは返らない。
- **学習時の除外** — `third_party/SDT/data_loader/loader.py` は日本語データに `max_len = 150` を適用し、150点以上のサンプルを学習から除外している。つまり配布チェックポイントは最も長い軌跡の字を一度も見ていない。多画数字は学習分布の外れ値であり、収録字であっても品質が落ちる。
- **失敗の隠蔽** — 生成結果は `place_glyph()`(`core/nohandwrite/metrics.py`)で bbox 正規化され枠の0.90倍に拡大される。途中で切れた鬱も「フルサイズの変な字」に引き伸ばされ、一見して失敗と分からない。

また、品質チェックもリトライも一切ない。1回の出力をそのまま採用している。

> **訂正(対策1実装時に判明)**: 当初「GMMサンプリングにより出力は確率的」と書いていたが、これは誤り。`third_party/SDT/models/gmm.py` の `get_seq_from_gmm()` は混合成分もペン状態も **argmax** を取るだけで、サンプリングしていない。同じスタイル画像・content画像を与えれば毎回まったく同じ軌跡が出る。したがって単純に再実行してもbest-of-Nにならず、**スタイル参照文字を引き直す**ことが唯一の変動要因になる(15字を書き手の全収録字から抽選しているため)。

### (b) 未収録字が生成できない仕組み

- 生成可能な文字は `third_party/SDT/data/TUATHANDS_JAPANESE/Japanese_content.pkl` のキー **4229字ちょうど**(漢字4052+かな169+英数記号)。`sdt_adapter.py` の `supports()` はこの辞書の存在チェックであり、鹵は収録されていない(鬱・鑑・驚は収録あり)。
- content画像の実体は**64×64のフォントレンダ画像**にすぎない。SDTのcontent入力は原理的に zero-shot なので、フォントで欠字をレンダして辞書を拡張すれば**推論だけで生成できる可能性が高い**。`character_dict.pkl` は学習時のID引きにのみ使われ、推論には不要。
- サーバー(`server/main.py` の `_render_chars`)は「辞書に無い」と「デコード失敗(ストローク0本)」を同じ `"生成辞書にない文字です"` で返しており、UI上で区別できない。
- `SDT_Tuning_Plan.md` は辞書外文字を明示的にM5対象外としている(「生成できない文字は手書きで埋める運用」)。本ドキュメントの対策2はその穴を埋めるもの。

## 対策1: 再学習なしで今すぐできること(短期) — **実装済み**

- **`MAX_SEQ_LEN` の引き上げ(120→200)** ✅ — 実測すると鬱は142点、鑑129点、驚134点で自然停止した。120では多画数漢字58字中5字(42%)が打ち切られていたが、200では0%になった。
- **途中打ち切りの検出** ✅ — `decode_sequence()` が `(strokes, completed)` を返す。`completed=False`(s3未出現)は `Generated.ok` を落とし、サーバーは `mode="generated_weak"` + `reason_code="truncated"` で返す。
  - ただし **bbox拡大の抑止は見送った**。打ち切られた字がどれだけ欠けているかを知る基準がなく(SDT出力は絶対スケールを持たない)、縮小率を決められない。代わりにUIで橙枠+警告文+逃げ道ボタンを出して失敗を明示する。
- **best-of-N リトライ** ✅ — `SDTGenerator.generate(attempts=3)`。**不合格の字だけ**引き直すので、ほとんどの字は1回で済み推論コストはN倍にならない。上記の訂正のとおり、変動はスタイル参照15字の引き直しで作る。
  - スコアは `content_similarity()`: 生成ストロークとcontent画像を **同じ bbox に合わせて**64×64にレンダし、互いの被覆率(precision/recall)の平均を取る。軸ごとに引き伸ばして合わせないと一・二のような平たい字が0点になる。クリーン出力58字で0.55〜1.00(中央値0.81)、しきい値は `SCORE_OK = 0.65`。
  - 画数チェック ✅ — 期待画数は `scripts/build_stroke_counts.py` がTUAT学習LMDB(215万サンプル)から書き手ごとの中央値を集計し、`core/nohandwrite/generate/stroke_counts.json`(4229字)に保存。辞書の画数ではなく「実際に何画で書かれているか」なので連綿の分だけ少なめ。`MIN_STROKE_RATIO = 0.6` を下回れば引き直す。
- **エラーメッセージの分離** ✅ — `server/main.py` の `FAIL_REASON` で `model_missing` / `unsupported`(辞書に無い) / `decode_failed`(ストローク0本) / `truncated` / `few_strokes` / `low_score` を `reason_code` として返す。
- **UIの逃げ道** ✅ — 生成セルに「↻ 再生成」「✏️ 自分で書く」(`/?char=X&writer=Y` へリンク)。辞書に無い字など引き直しても無駄なものには再生成ボタンを出さない。ツールチップに一致度・ストローク数・打ち切り有無を表示。

## 対策2: content辞書の拡張で未収録字に対応(中期)

- **欠字をフォントからレンダして追加する** — 学習時のcontent画像と近い明朝系フォント(Noto Serif CJK など)で欠字を64×64にレンダし、追加分を別ファイル(例 `data/content_ext.pkl`)として保存。`sdt_adapter.py` の `content` プロパティでマージロードする。SDT配布物(`Japanese_content.pkl`)は書き換えない。
- **対象の選び方** — 必要になった字を都度追加する運用でも、常用外・人名用漢字などの一覧から一括生成してもよい。1字=64×64画像1枚なのでサイズはほぼ問題にならない。
- **注意点** — 未収録字は zero-shot 生成になるため、収録字より品質が落ちる可能性がある。対策1の best-of-N・画数チェックと組み合わせ、ダメなら「自分で書く」に誘導する。

## 対策3: ファインチューニングでの根治(長期・M5連携)

`SDT_Tuning_Plan.md` のM5計画への差分として:

- **長軌跡サンプルを学習に含める** — M5.2で自分のデータに適用予定のRDP/等弧長リサンプリングを、**TUATの150点超サンプルにも適用**して150点未満に圧縮し、学習セットに復帰させる。多画数字が学習分布に入ることで根本的に品質が上がる。
- **学習側 `max_len` の緩和** — リサンプリングと択一ではなく併用も検討(例: `max_len=200` + リサンプリング)。メモリと学習時間への影響はNVIDIA機で要計測。
- 未収録字を本格対応するなら、対策2で作ったcontent画像+書き手数人分の実書字サンプルを追加してファインチューニングする道もあるが、データ収集コストが大きいので優先度は低い。

## 検証方法

- **ビジュアルグリッド** — 崩れやすい多画数字(鬱・鑑・驚・欝・麗・襲・鷹・囊など)+未収録字(鹵など対策2で追加した字)を並べた生成グリッドを対策の前後で出力し、目視比較する。M5.4のグリッド評価と同じ枠組みを使う。
- **定量評価** — 打ち切り検出の導入後、「s3未出現で終了した文字の割合」を崩壊率の代理指標としてログに出す。best-of-N導入後はスコア分布も併せて確認。
- **回帰確認** — 短い字(かな・低画数漢字)の見た目が変わっていないことをスタイルセット収録字で確認。M5.4のDTW評価と整合を取る。
